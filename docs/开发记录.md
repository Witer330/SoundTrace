### M2 波形播放器 ✅

- ffmpeg 流式解码 → 100ms 分辨率峰值（3 小时 ≈ 108,000 点），存 BLOB 复用
- Canvas 自绘波形：已播青色 / 未播暗蓝、点击与拖动跳转、平方根幅度缩放
- 播放 / 暂停（空格）、后退 10s、前进 30s、0.5~3x 倍速、书签（B 键，可命名、点击跳转、删除）
- asset 协议运行时放行库目录，`convertFileSrc` 播放

**播放放行验证**（`cargo test --test asset_scope`）：复现 Tauri `push_pattern` / `canonicalize_parent` / `Scope::is_allowed` 的路径规范化过程，确认 ① 归档音频被放行、② 递归覆盖嵌套子目录、③ 库目录外文件与兄弟目录被拒绝、④ Windows `\\?\` verbatim 前缀模式同样匹配。注意 `glob::Pattern::escape` 会转义 `*`，通配符必须转义路径后再单独拼接（Tauri 的 `escaped_pattern_with` 即如此）。


### M3 离线转写 ✅

- **引擎**：sherpa-onnx 1.13.8（静态链接 Rust crate）

  - 标点：CT-Transformer zh-en-vocab272727 int8
- 流水线：ffmpeg 转 16k 单声道 → VAD 分段 → 逐段 Paraformer 识别 → 字符时间戳映射到全局时间轴 → 标点恢复
- 模型管理器（设置页）：分项状态、下载进度事件、断点续传（`.part` 临时文件 + 已存在跳过）
- 后台工作线程：轮询 pending 任务、进度事件、可取消、重启后 running → pending 自动续跑
- 转写稿面板：虚拟滚动、**点字跳转音频**（字符级）、点击分段跳转、跟随播放自动滚动、稿内搜索（Enter 跳转 + 高亮）

**验证**：`cargo test e2e_chinese_transcription` —— Windows TTS 生成中文会议语音 → 全流程转写，识别文本与原文逐字一致（含标点与数字），时间戳单调递增。约 23s 完成 30 秒音频（首次含模型加载）。

### M5 设计令牌与双主题 ✅

- **做法**：`src/styles.css` 的 `@theme` 改为 `@theme inline`，色阶（`ink` / `mist` / `*-accent`）改为引用 `--st-*` 变量，深色默认在 `:root`、浅色在 `:root[data-theme="light"]` 覆盖
- **收益**：8 个视图文件里 257 处颜色类名**一处未改**，只换变量值即整体切主题。带透明度的类（`bg-ink-900/60`）编译为 `color-mix(…, var(--color-ink-900), …)`，运行时同样跟随覆盖
- 语义说明：色阶名是「槽位」不是字面颜色 —— 浅色下 `ink-950`（页面底）是近白、`mist-200`（主文字）是近黑，明暗关系整体反转
- 新增语义状态色 token `st-ok / st-warn / st-info / st-err / st-muted` 及 `-soft` 变体，替换写死的 `emerald-900/60` 这类（浅色下不可读）；新增说话人着色 `spk-1/2/3`；补 `mist-100`（原为未定义死类，`SummaryPanel` 里静默失效）
- 主题模式：跟随系统 / 深色 / 浅色；`index.html` 内联脚本在首帧前定主题消除启动闪烁；偏好存 localStorage；`color-scheme` 同步（滚动条与原生控件跟随）
- `Waveform.tsx`：Canvas 4 处硬编码 hex 改为运行时读 CSS 变量，并把已解析主题放进 `draw` 依赖（否则暂停状态下切主题波形不重绘）
- `SummaryPanel.tsx`：移除未生效的 `prose-invert`（未装 typography 插件），改用显式的 `.md-body` 排版规则

**验证**：编译产物确认为 `var(--st-ink-950)` 而非内联值；浏览器实测三段切换 —— body / 卡片 / 边框 / 文字 / 强调色整体切换、`color-scheme` 同步、localStorage 持久化、选中态正确。

### M6 工作台外壳与处理队列 ✅

- **信息架构判断**：参考稿（PM 工作台）以「项目」为中转层，声迹的原子单元是单条录音，因此首页主体是**处理队列**而非项目卡片流；不引入项目分组，靠标签 + 全文搜索归拢
- 侧栏改为 工作台 / 录音库 / 全文搜索 / 设置（带图标与激活态），工作台项显示待处理角标
- **工作台首页**：4 张统计卡（录音总数 / 待处理 / 本周完成转写 / 累计音频时长）+ 处理队列（进行中带进度条与取消、排队中显示队列位次、终态显示相对时间与失败原因）+ 最近录音
- **批量转写**：录音库复选框多选 + 全选 + 状态筛选（全部/待处理/已转写/失败），底部批量操作条一次排队（已有任务在跑的自动排除并汇总提示）
- 全文搜索从录音库抽出为独立视图（自动聚焦、防抖 350ms、片段命中直达时间点）
- `job://progress` 事件刷新合并 200ms，批量入队不再抖动 N 次全量查询
- 后端新增 `list_jobs(activeOnly)`：JOIN recordings 带出标题与时长，排序 running → pending → 终态，与 worker 的 FIFO 取件一致
- **修缺陷**：`cancel_transcribe` 原来只把 job 置 canceled，不回写 `recordings.status` 也不发事件 —— 取消一条排队中的录音后列表会一直显示「排队中」。现在同步回写并 emit；若该录音此刻已是 done（取消与 worker 完成竞争），不降级状态

**验证**：`cargo test --test queue` —— 故意乱序插入后断言排序（不靠 id 侥幸）、标题 JOIN、`activeOnly` 过滤、孤儿任务（无关联录音）不让查询整体失败。

- 新增 `ErrorBoundary`：单个视图渲染抛错不再整屏白屏，展示错误与组件调用栈并可重试
- 修两处会白屏 / 丢功能的缺陷：
  1. `PlayerBar` 在纯浏览器下调用 `convertFileSrc` 会读不存在的 `__TAURI_INTERNALS__` 而抛错 —— 详情页一渲染就白屏；改为先判断运行环境
  2. 从全局搜索跳转的定位在波形加载期间会被静默丢弃（播放器尚未挂载、audio 元素不存在），已把加载状态纳入依赖

**验证**：`cargo test --test segments` 四个用例 —— 合并规则（跨录音拒绝、夹层拒绝、时间轴去重且单调）、拆分的两半区间与时间轴、说话人名字读写与按录音隔离、「重新转写会覆盖手改分段」的行为固定（将来若改为保留手改，断言会提醒同步改提示文案）。

## 已知缺陷

### 转写在特定内容上会让应用闪退（2026-09-18 定位，未修复）

用用户真实录音（61 个文件 / 60.8 小时）做全流程验证时发现：**部分录音转写到中途，应用进程直接退出**。
用户侧表现为「转写跑一半闪退」，并在日志里留下 `CrashSender.exe` 相关的系统提示。

**根因**：`sherpa-onnx` 的 Paraformer 解码（`OfflineRecognizer::decode`）在**特定音频内容**上会破坏
栈保护，触发 `0xc0000409 / FAST_FAIL_STACK_COOKIE_CHECK_FAILURE`，Rust 运行时随即以
`fatal runtime error: Rust cannot catch foreign exceptions` 终止进程。崩溃发生在原生库内部，
Rust 侧无法用 `Result` 或 `catch_unwind` 兜住。

**已确立的事实**（每条都有可复现实验）：

| 结论 | 证据 |
|---|---|
| 崩在 `decode()` 内部，原生缺陷 | 探针逐行打印，崩在 `rec.decode(&stream)` 那一行，之前之后都能正常输出 |
| 与构建优化无关 | debug / release 均复现同一崩溃码 |
| 与音频时长**无单调关系** | 同一条录音：2 秒、6 秒片段必过；15~20 秒片段可过；一段 **3.33 秒**的片段必崩 |
| 与线程数无关 | num_threads = 1/2/4/8/20 都会崩，线程数只改变复现概率（1 线程最不易，但仍会崩） |
| 是**内容相关**，不是系统性缺陷 | 普通片段连续解码 40 轮**零崩溃**；问题片段约每 10 轮崩一次 |
| 不是编码/电平/声道问题 | 重编码（AAC 重编）、重采样（soxr）、±6dB 增益、100Hz 高通全部照崩 |
| 不是 VAD 的问题 | 单独跑 VAD 处理崩溃片段正常完成（4 段，最长 15.29 秒） |

**最小复现**（可复现的方法）：从 `~/Documents/录音/2026年09月02日 15点06分.m4a` 的 9937.5 秒处
取 3.33 秒 → 16k 单声道 WAV → 交给识别器解码，必崩。复现工具：
`cargo test --release --test real_library probe_vad_or_asr`（`ST_PROBE_WAV` / `ST_PROBE_MODE=raw` /
`ST_PROBE_THREADS` / `ST_PROBE_REPEAT`）。

**已尝试且无效的规避手段**（不要再重复试）：
- 把长片段按 6 秒切片送入识别器 —— 触发内容本身只有 3.33 秒，切不动
- 降低 `num_threads` —— 只降低概率，不消除
- 重采样/增益/滤波/重编码 —— 完全无效
- 裁掉音频开头做偏移 —— 结果非单调（裁 0.1s 崩、0.2s 不崩、0.3s 又崩），说明是「内容 + 模型内部
  张量形状」的交互，靠预处理躲不掉

**真正的修法**（待实施）：把转写流水线放到**独立子进程**里执行，父进程（Tauri 主程序）等待结果：
- 子进程崩了，父进程只是收到非零退出码 —— 应用不再闪退
- 可据此把任务标记为失败并给出可读原因，或跳过问题片段继续
- 现有 `run_pipeline` 已经是与 UI 解耦的纯函数，包一层 CLI 入口即可复用
- 代价：需要把模型加载放进子进程（每个任务多几百毫秒），崩溃恢复逻辑要写

**影响范围**：不是所有录音都会触发（61 个文件里已知至少 1 条；普通内容 40 轮重复解码零崩溃），
但长会议长时间跑必然踩到。在修复前，建议用户在转写时留意进度条——若应用消失，说明命中了这个缺陷。

## 已知边界

- 转写仅 CPU（RTF ≈ 0.12~0.22，8 核；3 小时录音约 22~40 分钟）
- 首次使用需在设置页下载模型（约 310MB，存于 `~/SoundTrace/models`）
- ffmpeg / ffprobe 需在 PATH（转码、峰值、解码均依赖）
- AI 复盘需自备 LLM API Key（录音不外传，仅转写文本发送）
