### M5 设计令牌与双主题 ✅

- **做法**：`src/styles.css` 的 `@theme` 改为 `@theme inline`，色阶（`ink` / `mist` / `*-accent`）改为引用 `--st-*` 变量，深色默认在 `:root`、浅色在 `:root[data-theme="light"]` 覆盖

- 语义说明：色阶名是「槽位」不是字面颜色 —— 浅色下 `ink-950`（页面底）是近白、`mist-200`（主文字）是近黑，明暗关系整体反转

- 主题模式：跟随系统 / 深色 / 浅色；`index.html` 内联脚本在首帧前定主题消除启动闪烁；偏好存 localStorage；`color-scheme` 同步（滚动条与原生控件跟随）
- `Waveform.tsx`：Canvas 4 处硬编码 hex 改为运行时读 CSS 变量，并把已解析主题放进 `draw` 依赖（否则暂停状态下切主题波形不重绘）
- `SummaryPanel.tsx`：移除未生效的 `prose-invert`（未装 typography 插件），改用显式的 `.md-body` 排版规则

**验证**：编译产物确认为 `var(--st-ink-950)` 而非内联值；浏览器实测三段切换 —— body / 卡片 / 边框 / 文字 / 强调色整体切换、`color-scheme` 同步、localStorage 持久化、选中态正确。

## 已知缺陷

### 转写在特定内容上会破坏栈保护（原生层缺陷，已通过进程隔离兜住）

用真实录音（61 个文件 / 60.8 小时）做全流程验证时发现：**部分录音转写到中途，进程直接退出**。
用户侧表现为「转写跑一半闪退」，并在日志里留下 `CrashSender.exe` 相关的系统提示。

**根因**：`sherpa-onnx` 的 Paraformer 解码（`OfflineRecognizer::decode`）在**特定音频内容**上会破坏
栈保护，触发 `0xc0000409 / FAST_FAIL_STACK_COOKIE_CHECK_FAILURE`，Rust 运行时随即以
`fatal runtime error: Rust cannot catch foreign exceptions` 终止进程。崩溃发生在原生库内部，
Rust 侧无法用 `Result` 或 `catch_unwind` 兜住——**这个缺陷本身修不了**（要改 sherpa-onnx 源码）。

**已确立的事实**（每条都有可复现实验）：

| 结论 | 证据 |
|---|---|
| 崩在 `decode()` 内部，原生缺陷 | 探针逐行打印，崩在 `rec.decode(&stream)` 那一行 |
| 与构建优化无关 | debug / release 均复现同一崩溃码 |
| 与音频时长**无单调关系** | 同一条录音：2 秒、6 秒片段必过；15~20 秒片段可过；一段 **3.33 秒**的片段必崩 |
| 与线程数无关 | num_threads = 1/2/4/8/20 都会崩，线程数只改变复现概率 |
| 是**内容相关**，不是系统性缺陷 | 普通片段连续解码 40 轮**零崩溃**；问题片段约每 10 轮崩一次 |
| 不是编码/电平/声道问题 | 重编码、重采样、soxr、±6dB 增益、100Hz 高通全部照崩 |
| 不是 VAD 的问题 | 单独跑 VAD 处理崩溃片段正常完成（4 段，最长 15.29 秒） |

**最小复现**：从 `~/Documents/录音/2026年09月02日 15点06分.m4a` 的 9937.5 秒处取 3.33 秒 →
16k 单声道 WAV → 交给识别器解码，必崩。复现工具：`cargo test --release --test real_library
probe_vad_or_asr`（`ST_PROBE_WAV` / `ST_PROBE_MODE=raw` / `ST_PROBE_THREADS` / `ST_PROBE_REPEAT`）。

**已证伪的规避手段**（不要再重复试）：按 6 秒切片（触发内容本身只有 3.33 秒）、降线程数（只降概率）、
重采样/增益/滤波/重编码（无效）、按偏移裁头部（结果非单调：裁 0.1s 崩、0.2s 不崩、0.3s 又崩，
说明是内容与模型内部张量形状的交互，预处理躲不掉）。

### 解法：转写进程隔离（已实施）

既然修不了原生库，就让它**崩在自己的进程里**。转写流水线移到独立子进程
（`src/bin/st-transcribe.rs`），父进程（Tauri 应用）只等它的退出码：

```
主程序 ──spawn──> st-transcribe <rec_id> <audio> <models> <cache> <out.json>
                 │ stdout 逐行 JSON 进度 ──> 主程序转发为 job://progress 事件
                 └ 退出 ──> 主程序读 out.json：分段数组=成功 / {"error"}=失败
```

- 子进程崩溃 → 父进程只收到非零退出码，**应用不再闪退**
- 崩溃的任务在队列里置为 `failed`，并写明可读原因（含退出码与引擎输出），可稍后重试
- 正常任务不受影响，批量转写不再「一崩全停」
- 取消改为杀掉子进程（`taskkill /F`），排队中的任务仍走状态回写
- 协议与退出码翻译见 `src/job_runner.rs`；收尾入库逻辑抽为可测的 `finalize_job`

**测试**（`cargo test`，20 个用例）：
- `tests/real_library.rs::child_process_isolates_native_crash` —— 用已知崩溃音频跑子进程，
  断言子进程异常退出、崩溃前进度已送出、**父进程存活**。若有人把转写改回进程内执行，
  这个测试会以「测试进程自己被 0xc0000409 带走」的方式失败
- `tests/job_finalize.rs`（5 个）—— 崩溃后任务置 failed 且原因可读、取消后录音回到 imported
  可重排队、成功时整批替换旧分段（不叠加）、成功路径状态与分段正确落库，以及成功路径的
  父子进程协议闭环（真实音频 → 子进程 → 进度流 → 结果文件 → 入库，首段文本与结果一致）

**打包注意**：转写引擎是独立外部二进制，必须与主程序一同分发。
- `bundle.resources` 引用 `binaries/st-transcribe.exe`（固定名，跨平台稳定）；
  `tools/build-sidecar.mjs` 负责把它构建成真货（同时产出一份带目标三元组的副本便于辨认）
- `build.rs` 在该文件缺失时放一个**占位文件**，避免全新克隆连 `cargo test` 都跑不起来
- 运行时查找顺序：主程序同目录 → 上一级 → `<主程序目录>/Resources/`。
  已验证打包后引擎落在**应用目录**（`PFiles\SoundTrace\st-transcribe.exe`），第一条即命中
- 打包命令不变：`pnpm tauri build`（`beforeBuildCommand` 已包含 sidecar 构建步骤）
- 若打包后转写报「找不到转写引擎」，检查安装目录里有没有这个 exe

## 转写的 CPU 占用策略

转写是纯 CPU 计算，早期版本按「全部逻辑核心」开线程，导致一转写整机满载、用户没法做别的事。
现在改成两条策略，都在 2026-09-18 用真实录音实测过。

### 1) 进程优先级：低于前台，固定常开

转写子进程（`st-transcribe.exe`）与导入转码 / 波形峰值解码的 ffmpeg 都以
`BELOW_NORMAL_PRIORITY_CLASS` 启动（`src/priority.rs`，走 `CommandExt::creation_flags`，
不引入新依赖）。Windows 调度是优先级抢占式的，所以：

- 机器空闲时转写照常拿满 CPU，**速度零损失**（优先级只在争抢时生效）；
- 用户一动手，前台程序立刻拿回 CPU，转写让路。

另有一条 CreateProcess 规则顺手覆盖了整条链路：未指定优先级类时子进程继承创建者的优先级类，
所以子进程内部那次 ffmpeg 解码（整文件重解码，是转写链路里的第二个重活）会自动跟着降下来。

### 2) 线程数：物理核心数，而不是逻辑核心数

`sherpa-onnx` 的 `num_threads` 曾取「全部逻辑核心」。实测发现这在带超线程 / 大小核的机器上
**反而更慢**：多出来的线程落在线程超售的 HT 兄弟与 E 核上，互相抢执行单元。

实测曲线（i5-14600KF：6P+8E，14 物理 / 20 逻辑核心；10 分钟真实会议音频；int8 Paraformer；
同期机器有约 25~35% 的后台负载，取多次运行的最小值）：

| 线程数 | 6 | 10 | 12 | **14** | 16 | 18 | 20 |
|---|---|---|---|---|---|---|---|
| RTF | 0.026 | 0.026 | 0.026 | **0.028** | 0.032 | 0.046 | 0.056 |

平坦区正好停在物理核心数（14），越过它开始变慢：**20 线程比 14 线程慢一倍以上**。
所以「自动」档取物理核心数，并保留至少 2 个逻辑核心给系统；物理核心数探测失败时退回
「逻辑核心 - 2」。实现见 `src/cpu.rs`（`GetLogicalProcessorInformationEx`，手写 extern 声明，
避免为此引入 windows-sys 依赖）。

用户在设置页「转写性能」可覆盖：`自动（推荐）` / `全部核心` / `自定义 N`，
存 `settings.perf.asrThreads`（`auto` | `all` | 正整数），在**任务开始时**读取，不作用于正在跑的任务。

复现这张表（`ST_ASR_THREADS` 覆盖设置，测试会打印实际线程数与每文件 RTF）：

```bash
cd src-tauri
# 用一个具体文件、只跑 1 条，避免目录扫描与批量带来的噪声
ST_ONLY_FILE="<某个 10 分钟左右的音频>" ST_VERIFY_N=1 ST_ASR_THREADS=14 \
  cargo test --test real_library real_recordings_full_pipeline -- --nocapture
```

> 量测要点：这台机器常年有 25~35% 的后台负载（Java / 远程桌面 / 微信等），**单次测量完全不可信**
> （同一配置曾测出 47 秒与 113 秒）。上表的做法是：不同线程数**交替**跑、每个配置多跑几次取
> **最小值**，并把每次的 CPU 占用一并记录。绝对 RTF 不必跨机器比较，比值才有意义。

> 顺带修掉一个前端契约缺陷：`AppInfo` 少了 `#[serde(rename_all = "camelCase")]`，前端读
> `info.dataRoot` 一直是 `undefined`，设置页「存储」卡片因此永远显示「…」。现已补上并加了单测守住。

## 说话人自动分离（V2，2026-09-19）

**问题**：一个人讲话的语气/语速变化会把声纹聚类拆成多个「说话人」；自动阈值模式下同一条
录音能聚出 60+ 簇，根本不可用。

### 参数语义实测（先用 examples/diar_spike.rs 拿数据，再写产品代码）

| 结论 | 证据（12.5 分钟真实会议音频） |
|---|---|
| `threshold` 是**余弦距离**，越大聚类越少 | 300 秒截取：0.35→74 簇、0.40→65、0.45→58、0.50→50、0.65→33 |
| 自动阈值救不回来 | 提到 0.85 仍有 10 簇（吸收后 4 簇），主讲人仍被拆成两半 |
| **锁人数一击命中** | 强制 3 人 → 10.4% / 88.8% / 0.9%，吸收后干净的两人分布 |
| `min_duration_on` 0.3→0.6 碎片减半 | 短片段占比 38% → 20% |
| 小簇吸收有效且便宜 | 占比 <5% 的簇并入接触最多的邻簇；孤立碎片并入最大簇 |
| 「重叠多数」映射够用 | 93 条转写分段：主导占比中位 0.94，88% 可靠取多数，<0.7 的 12% 不标注留给手工 |

> 教训：动手前先确认参数方向。sherpa-onnx 的 threshold 方向与直觉相反（上一版文档里
> 「越大聚类越多」的说法是错的，已用实测数据修正）。

### 产品化方案

- **人数必填**（`num_clusters`，1~32）：预填自「参会人」字段（按分隔符计数），存
  `settings.diar.clusters.<recording_id>`；分错了改个数重跑，16 分钟音频全片分离只要几分钟。
- **子进程隔离**（`src/bin/st-diarize.rs`）：与转写同一工程约束——原生库有破坏栈保护的
  前科。协议同一套：stdout 行式进度 + 结果文件（`diar::DiarOut`：成功 `{segments, numSpeakers}` /
  失败 `{"error"}`），崩溃翻译复用 `job_runner::explain_child_exit`。
- **后处理在子进程内完成**：吸收（`diar::absorb_spurious`）→ 簇号归一化为 1..k
  （`normalize_ids`，前端按 1 起编号配色/命名）。
- **任务队列化 + 转写完自动接续**（2026-09-19）：分离任务进 jobs 表（kind='diarize'），
  常驻 `DiarizeWorker` 串行执行（与转写 worker 同构：工作台可见、可取消、重启 running → pending 续跑）。
  人数选择在转写**之前**即可预设（选择即持久化到 `diar.clusters.<id>`）；转写收尾成功后
  检测到预设就自动入队分离——「预设人数 → 一步到位」的产品路径。
  不知道人数的历史录音不受影响：不预设就没有分离任务，仍走「批量转写 → 人工回忆人数 → 逐条分离」。
- **运行状态在后端**：运行槽（rec, pid, progress）+ `diarize_status` 命令，页面切走再回来
  也能查到真实进度；页面事件只是增量更新。
- ⚠️ **锁规则**：`finalize_job` 成功分支持有 `conn` 锁，里面的 DB 读取必须用已持有的
  guard 直接查——曾改用 `db.get_setting()`（内部再抢同一把非重入锁）导致转写收尾自死锁，
  表现为「转写永远停在 running」。凡在锁内调用 `Db` 的方法前，先确认它不重复加锁。
- **映射在父进程**（`diar::map_speakers` + `lib::finalize_diarize`）：按重叠时长取主导
  说话人，主导占比 ≥0.7 才标注；**只回填 `speaker_edited=0` 的段**——schema v5 新增
  `segments.speaker_edited`，手工标/改/清过的说话人绝不被自动分离覆盖（章程红线）。
- **合并修正**：`merge_speakers` 命令把拆错的簇一键并回（一条 UPDATE），移动的段标记
  `speaker_edited=1`，之后的自动分离不再碰它们。
- 模型：pyannote-segmentation-3.0（包内取 fp32 `model.onnx`，约 6MB）+ CAM++ zh
  （28.3MB），下载 URL 已核实，设置页模型列表自动带上；布局 `seg/model.onnx`、
  `speaker/campplus_zh_16k.onnx`（与 spike 时期一致，老用户零迁移）。
- 进度无内部回调（分离是单次推理调用），UI 报阶段点（解码/加载/推理），并明示
  「整段推理中，无精确进度」。

### 测试（tests/diarize.rs，4 个用例）

- 子进程参数校验：参数不足 / 人数越界（0、非整数、99）→ 退出码 2；
- 收尾入库保护：自动段被覆盖、**手工标注的段保持原样**、计数只算真正回填的段；
- 端到端：女声（Huihui）+ 男声（Kangkang）TTS 拼接 30 秒 → 子进程锁 2 人 →
  两个说话人、前半/后半主导占比各 ≥80% 且互不相同（拼接缝跨界窗口允许存在）。

## 主题标题与标签检索（V6，2026-09-23）

手机导出的默认文件名（`REC_20260923_xxx`）无法承担"按事件/主题找录音"的检索需求。
设计决策：**标题即主题**——不加第三个名字字段，`orig_name`（溯源）+ `title`（显示）的二元结构
保持不变，只给 `title` 换内容来源：AI 纪要首行的主题短语自动回填，原名降级为元数据。

- **schema v6**：`recordings.title_edited`（默认 0），与 `segments.speaker_edited` 同一模式，
  落实章程"手工修改不可被自动覆盖静默丢失"。
- **首行解析**：`llm::parse_headline` 解析纪要首行引用块「> 类型 · 主题」，分隔符宽容
  `·`/`・`/`•`，缺分隔符整行当主题；首行不是引用块（旧格式纪要）返回 None 不回填。
  前端 `parseSummaryHeadline`（types.ts）同一规则，供列表类型徽章使用。
- **回填时机**：
  - summarize 收尾（`llm.rs`）：保存纪要后，`title_edited=0` 才回填标题；
  - 迁移 V6（`db.rs::backfill_titles_from_summary`）：存量有纪要的录音启动时纯解析回填，
    不调 LLM，老库立即受益。
- **误锁防护**：`update_recording` 只在标题值真的变化时才置 `title_edited=1`——详情页保存会
  原样带回未改动的标题，不能因此把自动回填锁死；详情页编辑框对未编辑的标题跟随后端
  （`titleDirtyRef`），否则纪要生成后点"保存"会把旧标题写回去。
- **prompt 微调**：FINAL/MERGE 的首行从"一句话概括（≤30字）"改为"主题短语（≤20 字名词短语，
  不用完整句不带句号）"——概括是叙述句，当列表标题太长。
- **前端**：库列表加标签筛选 chips（全库标签按出现次数排序，可叠加，行内标签可点击加入筛选）；
  行内显示 AI 识别的录音类型徽章；标题被主题替换后原始文件名显示在次行元数据里（悬停看全名）。
